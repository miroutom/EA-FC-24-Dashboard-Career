# Leicester City Analytics — ТЗ / MVP v0.2: Zero-Screenshot Edition

**Статус:** спецификация для реализации через Codex  
**Дата:** 28 октября 2026  
**Цель:** локальное, офлайн-дружественное веб-приложение для аналитики менеджерских карьер EA FC 24 с автоматическим получением максимально доступных данных через Live Editor + Lua, без регулярных скриншотов и ручного заполнения статистики.  
**Образец интерфейса:** присланные пользователем кадры дашборда RespectTheJeff (Summary, Matches, Squad/Overview/Table/Updates, Player drawer, AI Chat). Не копировать изображения/ассеты и не предполагать, что источник данных Джеффа автоматизирован.  
**Первая карьера:** Leicester City, исторический набор 2023/24–2027/28 (исходный файл `leicester_rebuilt_with_career_totals.xlsx`).  
**Архитектура:** несколько независимых карьер и сохранений; приложение запускается локально, без облака, регистрации, SaaS, платных API и обязательного Docker.

---

## 0. Главное продуктовое решение

### Суть

Игрок запускает EA FC 24 через совместимый Live Editor и играет/симулирует матчи карьеры. После первоначальной настройки система **сама** считывает доступные данные, сохраняет исторические снимки, вычисляет изменения и обновляет дашборд. Скриншоты, OCR, ручная форма «Добавить матч» **не являются обязательной частью процесса**. Единственное регулярно допускаемое действие пользователя — добавить необязательные `notes` к матчу/периоду.

**Нельзя утверждать, что полностью автоматизированы неподтверждённые источником метрики.** Не создавать фальшивые xG, владение, точность передач, соперников, индивидуальные оценки матча, минуты, реальный результат или рейтинг состава из сезонных агрегатов. Для неполных данных показывать `—`, `неизвестно` или `недоступно`, а не `0`.

### Критерий успеха пользователя

> Один раз настроил интеграцию → играю карьеру → открываю браузер → вижу актуальные сезонные и карьерные показатели игроков, динамику и источники данных; при желании дописываю комментарий. Не снимаю и не загружаю после каждого матча пачку скриншотов.

### Платформы

- **Сборщик Live Editor: Windows**, потому что сама EA FC 24/Live Editor работает на Windows; не обещать запуск Live Editor на macOS.
- **Локальное веб-приложение:** backend + frontend можно запускать там, где удобно, но *в MVP самый простой и обязательный сценарий — все компоненты на той же Windows-машине*. Если браузер открыт на Mac, доступ с другого устройства по LAN и синхронизация через сеть — отдельная настройка, не основной критерий MVP.
- EA FC 24 + совместимая версия FC 24 Live Editor, офлайн-карьера. Live Editor может быть несовместим с конкретной сборкой игры и имеет предупреждения автора о рисках античита: описать в README, **не пытаться обходить античит**.

## 1. Проверенная база и технические неизвестные

### Документированное

- `GetPlayersStats()` возвращает **накопленные показатели текущего сезона** по игрокам и турнирам: `teamid`, `playerid`, `compobjid`, `app`, `goals`, `assists`, `yellow`, `red`, `clean_sheets`, `avg` и некоторые дополнительные ключи; `avg` в документации указан как показатель, который нужно делить на количество появлений (`app`) для расчёта средней оценки. Достоверность дополнительных `motm`, `goals_conceded`, `saves` отдельно помечена автором как неопределённая.
- `GetPlayerStats(playerid)` позволяет читать эти данные для одного футболиста.
- Live Editor Lua API v2 предоставляет `AddEventHandler("post__CareerModeEvent", ...)`, а также события карьеры. Событие *не гарантирует*, что все статистические структуры уже окончательно обновлены в этот момент.
- Существуют готовые открытые примеры автоматического сбора **снимков развития игроков** через Live Editor (FC Career Top): можно исследовать подход, не копируя без проверки, что там есть поматчевая результативность.

### НЕ подтверждено заранее; обязателен эксперимент

- Какая именно последовательность событий корректно и одинаково работает после сыгранного, быстросимулированного и интерактивно симулированного матча.
- Становятся ли данные `GetPlayersStats()` актуальными уже на post-match event или только после возврата в меню/смены дня.
- Можно ли получить надёжные `match_id`, соперника, счёт, точную дату матча, игровую оценку **конкретного** игрока за матч, минуты, составы, xG/xGA, владение, удары и статистику отдельных встреч.
- Можно ли безопасно писать локальный файл штатным Lua `io`, в какую директорию, либо потребуется поддерживаемый Live Editor экспорт / альтернативный односторонний канал.
- Возможен ли автозапуск скрипта при каждой загрузке Live Editor без повторного ручного запуска.
- Стабильность `GetSaveUID()` и идентификаторов между сохранениями; нельзя использовать без верификации.

Все неподтверждённые возможности — через `capabilities` и feature flags. Никаких заведомо фиктивных «работающих» интеграций.

## 2. Поэтапная разработка и ворота качества

### Phase 0 / POC — **сначала**, технический риск

**Цель:** доказать на реальной EA FC 24, что можно автоматически сделать полезный снимок и обнаружить его изменение после матча; без этого нельзя обещать полноценную автоматизацию.

Реализовать:

1. `collectors/fc24-live-editor/diagnostic.lua` — безопасный read-only Lua-скрипт, который определяет факт нахождения в менеджерской карьере, версии, команду/дату/UID только если доступны; выводит в лог и сериализует небольшой набор статистики (`playerid`, `teamid`, `compobjid`, `app`, `goals`, `assists`, `yellow`, `red`, `avg`, `clean_sheets`). В диагностике — маскирование локальных путей/секретов в логах.
2. `event_probe.lua` — отдельный обработчик `CareerModeEvent` с журналированием ID и последовательности событий. Подключать один раз, не регистрировать дублирующие обработчики. Если константы `USER_MATCH_COMPLETED`, `POST_MATCH_REPORTS_DISPLAYED` присутствуют в `enums.lua`, использовать символические имена **после фактической проверки**. Не хардкодить ID без источника.
3. `scripts/diagnose_snapshots.py` — сравнивает `before`/`after` и печатает изменения по ключам игрок+турнир, не выдавая отрицательные дельты за отрицательные голы.
4. Подробная инструкция теста: (a) вход в карьеру и первый снимок, (b) один **сыгранный** матч, (c) одна **быстрая симуляция**, (d) повторное событие, (e) reload того же save, (f) переход сезона — по возможности без порчи основного сохранения (использовать тестовую копию).
5. `docs/capability-matrix.md`: `VERIFIED`, `PARTIAL`, `UNAVAILABLE`, `NOT_TESTED`, доказательство (лог/скрин в репозитории не обязателен), версии игры и Live Editor, тестированный сценарий.

**Gate P0:** есть фактический лог со статистикой минимум одного игрока до/после матча и установлен способ записи/передачи файлов в Python. До появления такого лога считать интеграцию **непроверенной** и реализовать её в экспериментальном режиме; Codex не должен выдумывать успешные результаты теста, если у него нет доступа к EA FC 24.

Если P0 заблокирован, продолжать разработку исторического дашборда (Phase 1), но **явно** указывать `Collector: not verified`; не заменять автоматический сбор ручным скриншотным процессом.

### Phase 1 / Base MVP — реальные исторические данные

- Monorepo; SQLite + миграции; Python API + React UI; поддержка множества карьер.
- Импорт XLSX/CSV и исторического «Лестера» за 2023/24–2027/28.
- Рабочие страницы `Overview`, `Squad → Table`, `Player Drawer`, `Player Profile/History`, `Compare`, `Sync Status`.
- Только подтверждённые из Excel показатели: сезон, имя, позиция, количество появлений, голы, ассисты, сухие матчи. Без выдуманной средней оценки, текущего состава, потенциала, трансферной стоимости, дат матчей.
- Общий рейтинг игроков за всю карьеру, число **учтённых** сезонов, первый/последний сезон; сезонные графики и фильтры.
- API и сущности заранее готовы для snapshot ingestion и поматчевой аналитики.

### Phase 2 / Automated MVP — **основной целевой релиз**

- Версионированный read-only collector читает статистику после установленных P0 событий/переходов. Сохраняет оригинальные снимки без удаления предыдущих.
- Python ingestion service наблюдает локальную очередь файлов, импортирует атомарно и идемпотентно, обновляет статусы.
- При каждой новой проверенной порции данных автоматически обновляются показатели по игроку, турниру, сезону; фронтенд перезапрашивает статистику.
- Страница `Sync Status`: connected/not connected, last snapshot, version, processed/ignored/error, причина ошибок, повторить импорт файла, текущая карьера/save binding, дата последней успешной синхронизации.
- Если последовательно полученные снимки достоверно принадлежат соседним матчам, показывать **inferred per-match deltas** (голы, ассисты, карточки, appearances). Иначе отображать изменение **между снимками/за период**, без ложной точности «за матч».
- Поле `notes` необязательное (ввод вручную только пояснения, не статистики).

**Gate P2:** после настроенного запуска игры (с учётом реально подтверждённого механизма активации Lua) можно сыграть матч **без скриншотов** и увидеть изменение статистики в UI. Если конкретная метрика недоступна — честно скрыта/недоступна. При перезапуске/повторной доставке нет двойного счёта.

### After MVP — отдельные задачи

- `Matches` с настоящим календарём/соперником/счётом при наличии достоверного источника.
- Поматчевая оценка, минуты, xG, владение, удары, стиль розыгрыша — **только** после подтверждения источника и точности.
- OVR/потенциал/возраст/трансферы и динамика на уровне недели, дополнительный collector по примеру FC Career Top.
- Турнирные таблицы и трофеи, результаты остальных чемпионатов.
- Squad Planning с реальными данными и опциональный AI Analyst (никакого внешнего LLM ключа в MVP).

## 3. Сценарии использования

**UC01 — первый запуск.** Открываю `localhost`, создаю карьеру `Leicester City`, выбираю `EA FC 24`, задаю начальный сезон `2023/24`, загружаю исторический Excel. Вижу суммарные и сезонные цифры, сведения об источнике и неполноте.

**UC02 — несколько карьер.** Добавляю новую карьеру (хоть с тем же клубом), переключаюсь между ними. Данные и save bindings никогда не смешиваются.

**UC03 — после матча.** Играю матч. Collector автоматически производит новый снимок (когда доказан корректный триггер), watcher обрабатывает файл, UI обновляется. Если связь прервалась, при возобновлении очередь догоняет историю.

**UC04 — проверка Сарра.** В Squad Table нажимаю на игрока, справа открывается drawer: выступления, голы, ассисты, Г+П, число учтённых сезонов, график по сезонам, вклад в команду (с оговорками), разбивка по турнирам, если есть. Виден признак `historical` vs `live`.

**UC05 — заметка.** В `Sync/Matches` могу добавить текст «Сарр вышел на замену и перевернул игру»; отсутствие заметки ни на что не влияет.

**UC06 — ошибка/откат сейва.** Если откатил карьеру на прошлую дату, система распознаёт немонотонность или нестыковки и помечает новую ветку/конфликт; не вычитает голы из исторических итогов автоматически и не затирает данные без выбора стратегии.

## 4. UI/UX по референсам Джеффа

**Дизайн:** dark charcoal background (`#11141E`-подобный), тёмные панели, светлый текст, неброская сетка, ясная типографика, синий Leicester как собственный акцент, зелёный/оранжевый для смысловых статусов (не красить всё подряд), горизонтальные KPI, компактные таблицы. Desktop-first 1440px; responsive до ~768px, без зависимостей от внешних фото/логотипов.

**Навигация MVP:**

- `Careers` — выбор карьеры/save; верхний persistent selector карьер и сезонов.
- `Summary` — KPI с поддержкой `All time / Season`, блок лидеров, сезонный график goals/assists; индикатор свежести данных/coverage. Вместо выдуманных `W/D/L`, `xG` — сообщаем «Нет поматчевых данных».
- `Squad → Table` — расширенная таблица: Игрок, позиция, учтённые сезоны, матчи, голы, ассисты, Г+П, goals/appearance, G+A/appearance; поиск, сортировка, фильтры.
- `Squad → Overview` — топ по голам/ассистам/матчам; сезонная динамика; **не** отображать «Средний OVR», пока нет этих данных.
- `Squad → Updates` — изменения по снимкам; если Live Editor ещё не подключён — осмысленный empty state.
- `Player Drawer` — открывается кликом по строке, не теряя фильтры; карьерные итоги, история сезонов, при наличии — рейтинги/развитие/форма, источник и уровень достоверности.
- `Compare` — 2–4 игрока, одинаковые фильтры, графики.
- `Sync Status` — обязательный для Automated MVP, прозрачная диагностика.
- `Notes` — необязательная заметка к конкретной подтверждённой встрече или интервалу; **не** требовать скриншоты и не запускать OCR.

**Matches:** до подтверждения конкретного match ID / соперника / счёта позволяется раздел «Между снимками», но нельзя называть такие записи достоверными матчами. Полный `Matches Overview` перенести за пределы MVP, если нет источника.

**Глобальные фильтры:** карьера, `All time` / отдельный сезон, турнир (только если есть турнирные данные), `Snapshot date` (если сбор активен). Все метрики зависят от фильтров.

**Состояния:** loading, empty, integration not configured, source partially known, stale sync, error, conflict, history incomplete.

## 5. Технологический стек и проект

- Frontend: **React + TypeScript + Vite**, Tailwind CSS, shadcn/ui, TanStack Table, TanStack Query, Recharts, React Router.
- Backend: **Python 3.12+, FastAPI, Pydantic v2, SQLAlchemy 2, Alembic**.
- Local DB: **SQLite** в папке данных приложения (`DATA_DIR`), с включённым `PRAGMA foreign_keys=ON`, WAL для чтения во время записи; индексы/constraints.
- Excel: `openpyxl` для рабочего приложения; CSV: стандартный `csv`. Базу данных не редактировать напрямую из frontend.
- Collector: **Lua** в Live Editor, read-only, только проверенные API; Python watcher / ingestion service.
- Test: pytest + frontend Vitest / React Testing Library; offline fixture-based tests, отдельный сценарий ручной валидации с игрой.
- No cloud, no accounts, no mandatory Docker; Vite dev proxy to FastAPI; сборка SPA обслуживается backend или отдельным локальным HTTP сервером.

## 6. База данных: точный принцип хранения

**Проблема:** сезонные суммы из Excel, накопленные сезонные показания Lua и вычисленные изменения **нельзя суммировать друг с другом** — получится двойной счёт. Снимки — это временные наблюдения одного и того же накопительного счётчика, а не новые голы сами по себе.

### Основные сущности

| Таблица | Поля / уникальность | Зачем |
|---|---|---|
| `careers` | id, name, game_version, primary_team_id, created_at | Разные карьеры |
| `career_saves` | id, career_id, external_save_uid nullable, instance_key, branch_no, status, bound_at | Изоляция сейвов и веток |
| `teams` | id, game_version, external_team_id nullable, name | Клубы |
| `seasons` | id, career_id, start_year, end_year, unique(career_id,start_year) | Сезоны |
| `competitions` | id, game_version, external_compobjid nullable, name, kind | Турниры |
| `players` | id, career_id, external_player_id nullable, display_name, normalized_name | Футболисты в контексте карьеры |
| `player_aliases` | player_id, alias, source | Безопасное сопоставление имён |
| `player_season_metadata` | career_id, season_id, player_id, team_id, age nullable, overall nullable, potential nullable, position nullable, observed_at | Данные состава, если подтверждены |
| `historical_aggregate_stats` | career_id, season_id, player_id, team_id, scope, competition_id nullable, appearances, goals, assists, clean_sheets nullable, source_batch_id, coverage | Первичные суммы Excel |
| `collector_snapshots` | id, career_save_id, in_game_date nullable, captured_at, event_name nullable, source_version, payload_sha256, status, raw_path, imported_at | Неизменённые наблюдения Lua |
| `collector_snapshot_rows` | snapshot_id, player_external_id, team_external_id, compobjid, appearances, goals, assists, yellow, red, clean_sheets, avg_raw, optional fields | **Полное** состояние счётчиков |
| `inferred_deltas` | id, previous_snapshot_id, next_snapshot_id, player/comp key, app_delta, goals_delta, assists_delta, etc., confidence, interval_label | Производные различия, НЕ ещё одна сумма |
| `matches` | id, career_save_id, season_id, competition_id nullable, source_external_match_id nullable, played_at nullable, opponent_id nullable, home_goals nullable, away_goals nullable, verified_source | Только достоверные встречи |
| `notes` | id, career_id, match_id nullable, interval_id nullable, text, created_at | Необязательные заметки |
| `import_batches` | id, career_id, filename, sha256, status, stats, created_at | Идемпотентность импорта |
| `sync_events` | id, save_id, snapshot_id, action, level, message, time | Диагностика |

Для `scope` использовать `ALL_COMPETITIONS` или `COMPETITION`; не делать одновременно две активные агрегирующие записи одного уровня, чтобы не удваивать суммы. Составные unique constraints и partial unique indexes там, где `competition_id` nullable (SQLite допускает несколько NULL в обычном UNIQUE).

**Идентичность:** `playerid` из игры — приоритетный идентификатор внутри конкретной карьеры/сейва. Имя — только alias/display. Исторические сокращения `J. Vardy` и `Jamie Vardy` сопоставлять по заранее проверенной карте или явно подтверждённым данным, не склеивать только по одинаковой фамилии. Если save UID недоступен — однократное явное связывание сохранения с карьерой, не автоматическая догадка.

### Query rules / single source of truth

1. Для выбранного игрока-сезона-турнира: **либо** historical aggregate, **либо** последний верифицированный LIVE cumulative counter, либо проверенное reconciled значение; **никогда не складывать historical и live**.
2. Накопленные Lua-значения разных дат не суммировать. Брать последнее достоверное значение в текущей непротиворечивой ветке сохранения.
3. Сезонная статистика на момент времени `as_of` — latest cumulative per player+competition within season+save branch.
4. Для «Все турниры» суммировать отдельные доступные турниры **только если учтён полный набор**; если источник содержит официальный total, использовать total как отдельный scope и не добавлять к нему competition rows.
5. `avg` — сохранить raw. Рассчитывать `avg / app` только после проверки единиц и кейсов в игре, иначе пометить unavailable. Усреднять оценки между турнирами взвешенно, не арифметическим средним от средних.
6. `seasons_count = COUNT(DISTINCT season_id)` по подтверждённым записям, включая 0 матчей. Отдельно подписывать «учтённые сезоны», а не продолжительность контракта.
7. `appearances` сумма игр конкретного футболиста, **не** число матчей команды. Голы игроков ≠ гарантированно точные голы команды (автоголы).
8. `per match` допустим только при `appearances > 0`; `per 90` — только при наличии minutes_played.
9. Отсутствие строки/поля ≠ ноль, для unknown хранить NULL/недоступность. Для snapshot отсутствующий игрок может быть трансфером/неучётом, не обнулять его карьерный итог.
10. Результаты иных команд/лиг не высчитывать из `GetPlayersStats()` как если бы API содержал полную мировую историю: документация ограничивает генерацию статистики набором соревнований.

### Снимки и дельты

- `raw_payload` сохраняется в immutable JSON файлами; БД хранит их хеш, метаданные, нормализованные строки.
- Natural key для снапшота: `(career_save_id, season_id, captured context, payload_sha256)` плюс технический UUID; выбирать устойчивый механизм идемпотентности с учётом одинаковых показаний до/после отсутствия изменений.
- Delta рассчитывать как `new_counter - previous_counter` по **playerid + teamid + compobjid + season + branch**.
- Если дельта <0, сменился сезон, неизвестная полнота, пропущены промежуточные события или загрузили более ранний сейв → `INVALID/AMBIGUOUS`, **не** применять как голы конкретного матча.
- Если `app_delta >1`, нельзя говорить «это один матч»; подписать «изменения за период».
- Если `app_delta =0`, но голы выросли, пометить противоречие, пока не исследован случай.
- Если `app_delta=1`, это **кандидат** для матча, но не доказательство единственного календарного события, пока event coverage не подтверждено.
- При откате сохранения: сохранить старую историю, отделить новую ветку `branch_no`, сделать в UI понятную подсказку. Не удалять и не править автоматически прошлые матчевые записи.
- Автоматическая повторная доставка одного JSON, повторный event и рестарт watcher — 0 дублей.
- Lua пишет во временный файл и переименовывает атомарно (если реально поддерживается файловой системой/API) либо Python ждёт устойчивого размера + checksum; при ошибке парсинга файл отправить в `quarantine/`, не терять оригинал.

### Контракт Lua → Python (`snapshot_v1`)

Ниже **формат нашего приложения**, НЕ заявка на то, что Live Editor готовым API возвращает все поля:

```json
{
  "schema_version": 1,
  "producer": "fc24-live-editor-lua",
  "collector_version": "0.2.0",
  "game_version": "EA FC 24",
  "captured_at_utc": "2026-10-28T12:00:00Z",
  "event": "career_snapshot",
  "save_uid": null,
  "in_game_date": null,
  "user_team_id": 95,
  "season_start_year": null,
  "rows": [
    {
      "playerid": 12345,
      "teamid": 95,
      "compobjid": 1,
      "app": 10,
      "goals": 8,
      "assists": 3,
      "yellow": 1,
      "red": 0,
      "clean_sheets": 2,
      "avg": 72
    }
  ]
}
```

**Все числа в этом JSON — демонстрационные, исключительно пример схемы, не данные пользователя.** Nullable идентифицирующие поля сначала могут быть неизвестны; importer должен пометить snapshot как `NEEDS_BINDING`, а не присваивать его произвольной карьере.

Валидация: `schema_version`, nullability, типы, counters >=0, известный `career_save_id`, допустимые переходы season/branch, запрет автоматического выполнения кода из payload. Ограничение размера файла, sanitization путей, настраиваемая папка spool, отсутствие сетевых команд от игровых скриптов.

## 7. Исторический Excel и миграция старых данных

Исходник: `leicester_rebuilt_with_career_totals.xlsx`.

- Импортировать **только** лист `Все сезоны`. Листы `2023-24`, ..., `2027-28` дублируют ту же статистику, а `За всю карьеру` содержит производные значения.
- Колонки: `Сезон`, `Игрок`, `Позиция`, `Матчи`, `Голы`, `Ассисты`, `Сухие матчи`, `Г+П`.
- `Г+П` пересчитывать в backend как `goals + assists`; не доверять кешу формулы.
- Колонку `Сухие матчи` сохранять так, как она дана в FIFA, в том числе для полевых игроков; не интерпретировать только как goalkeeper clean sheets.
- Варианты имён (`Hložek`, `Kadıoğlu`, `João`, и т. п.) должны сохранять Unicode; нормализация не должна стирать диакритику в display name.
- Видимые строки скриншотов — **частичная история**, не гарантированный полный состав. В UI `coverage=PARTIAL_SCREENSHOT`.
- Загрузка Excel через preview → validate → commit; SHA-256 для повторного файла; при конфликте — показывать детали и требовать одобрения, не складывать совпадающие строки.
- По мере появления Live данных для пересекающихся сезонов не складывать автоматически новые суммы с историческими. Выбирать приоритет только после reconciliation/ручного подтверждения соответствия и полноты.

## 8. API v1 (целевая форма)

Все `{career_id}` проверяются на принадлежность данных конкретной карьере. Для frontend JSON DTO через Pydantic, не возвращать SQLAlchemy напрямую.

```text
GET    /api/v1/health
GET    /api/v1/careers
POST   /api/v1/careers
GET    /api/v1/careers/{career_id}/seasons
GET    /api/v1/careers/{career_id}/dashboard?season_id=&competition_id=&as_of=
GET    /api/v1/careers/{career_id}/players?season_id=&competition_id=&search=&sort=&page=
GET    /api/v1/careers/{career_id}/players/{player_id}?season_id=&competition_id=
GET    /api/v1/careers/{career_id}/compare?player_ids=...&season_id=
POST   /api/v1/careers/{career_id}/imports/preview       (xlsx/csv multipart)
POST   /api/v1/careers/{career_id}/imports/commit        (preview_token + strategy)
GET    /api/v1/careers/{career_id}/imports
GET    /api/v1/careers/{career_id}/sync/status
GET    /api/v1/careers/{career_id}/sync/events
POST   /api/v1/careers/{career_id}/saves/bind             (one-time setup)
GET    /api/v1/careers/{career_id}/snapshots?save_id=&limit=
GET    /api/v1/careers/{career_id}/changes?player_id=&season_id=&confidence=
POST   /api/v1/careers/{career_id}/notes                 (optional)
```

Для desktop collector лучше использовать file watcher, а не открытый публичный ingest-эндпоинт. Если endpoint всё же есть, использовать только `127.0.0.1`, ограничение размера, проверку source, токен и защиту от подмены карьеры; никаких облачных credential.

- Ответы аналитики включают `data_quality`: `historical_partial`, `verified_live`, `inferred_interval`, `unknown`.
- Возвращать `last_synced_at` и `source_scope`.
- Параметры page/size ограничивать, сортировку — по whitelist.
- Неправильный save ID / player ID из другой карьеры → 404/409, не смешивать.
- Общие ошибки: 400/404/409/422; structured error DTO.

## 9. Acceptance criteria / готовность

### P0 — техническая верификация (без фальшивых выводов)

- [ ] Диагностический скрипт **собран и документирован** с точными вызовами API и обработчиками событий.
- [ ] Есть инструкции проверки на одном сыгранном и одном симулированном матче.
- [ ] Страница Capability Matrix честно показывает, что реально проверено, а что требует Windows + игры.
- [ ] Если доступа к игре нет, статус `NOT_TESTED`, а не `VERIFIED`.

### Base MVP

- [ ] Две карьеры существуют независимо и не смешиваются ни в одном endpoint.
- [ ] Исторический Excel импортируется только из `Все сезоны`, без двойного счёта.
- [ ] У игрока отображаются учтённые сезоны, `apps/goals/assists/G+A`, первый/последний сезон и динамика.
- [ ] Все итоги в интерфейсе рассчитываются из БД; нет mock stats в production.
- [ ] Отсутствующая оценка/OVR отображается `—`, а не выдуманным числом.
- [ ] Re-import того же файла не меняет суммы; конфликтующие строки не складываются.
- [ ] Тесты backend и frontend запускаются локально.

### Automated MVP (главное)

- [ ] Настроена локальная очередь Lua → Python: снапшот импортируется из JSON без скриншотов и ручного ввода полей.
- [ ] После доказанного момента обновления статистики снимок фиксируется автоматически, без постоянного нажимания кнопки «Экспорт».
- [ ] Повторный event и повторная доставка снимка идемпотентны.
- [ ] `GetPlayersStats` со значениями `app/goals/assists` по турнирам правильно обновляет агрегаты.
- [ ] Новый сезон не перезаписывает старый; откат сейва выявляется, не ломает историю.
- [ ] Дельты показываются как «между снимками», если нет достоверной привязки к конкретному матчу.
- [ ] `Sync Status` показывает статус, ошибки и реальную последнюю синхронизацию.
- [ ] `notes` можно добавить и не добавлять без влияния на сбор.
- [ ] В UI нет безосновательных xG, possession, match rating, результатов и соперников.

### Обязательные тест-кейсы

1. Тот же snapshot трижды → одна запись / ноль повторных начислений.
2. Два snapshot с `goals: 4 -> 6`, `app: 10 -> 11` → delta 2 гола без повторного суммирования totals.
3. `app: 10 -> 12` → изменение **за период**, не уверенное утверждение «в одном матче».
4. `goals: 8 -> 3` / откат save → `CONFLICT/ROLLBACK`, не `-5 goals`.
5. Новый сезон `2027/28 -> 2028/29` → независимые сезонные строки.
6. Одинаковое имя в двух карьерах → разные игроки.
7. Исторический TOTAL + Live competition overlap → без удвоения.
8. Часть полей отсутствует → NULL/`—`, не нулевые подстановки.
9. Невалидный JSON → quarantine + лог без частично сохранённой БД.
10. Прерванный импорт → атомарный rollback; успешный повтор допускается.
11. Изменение игрового часа/даты без матча → snapshot, но не «матч».
12. Имена с Unicode не ломают API, фильтры и импорт.
