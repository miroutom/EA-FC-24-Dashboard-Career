# Задание Codex: подготовить Leicester City Analytics на Windows до запуска EA FC 24

## Твоя задача

Ты — Codex на Windows-компьютере владельца. Подготовь существующий проект к первой проверке на настоящей менеджерской карьере EA FC 24. Выполни доступную подготовку и проверки самостоятельно. **Игру пока не запускай: пользователь запустит её после твоего отчёта о готовности.**

Репозиторий: **https://github.com/miroutom/EA-FC-24-Dashboard-Career**.

Это уже реализованное приложение, а не задание написать его заново. Стек: Python 3.12 / FastAPI / SQLAlchemy / Alembic / SQLite; React / TypeScript / Vite. Есть реальные исторические данные Excel, отдельное синтетическое демо и экспериментальные Lua-скрипты Live Editor.

Итог до запуска игры: рабочий локальный дашборд, установленные зависимости, пройденные доступные проверки, подготовленный конфиг диагностики, точные команды для Lua Engine и понятный отчёт. Отдельно перечисли поля и возможности, которые невозможно подтвердить без игры.

## Ограничения и текущая граница готовности

- Работай локально на той же Windows-машине, где будет EA FC 24. Cloudflared, Cloudflare Tunnel, ngrok, внешний хостинг и открытие доступа из интернета не нужны. Backend должен слушать только `127.0.0.1`.
- Не запускай EA FC 24 и Live Editor launcher автоматически. Не меняй античит, защиту Windows, бинарники игры и реальные сохранения. Не настраивай обход античита. Для дальнейшего опыта понадобится тестовая копия сохранения.
- Не смешивай реальные данные и демо. Обычный режим: `app.main`, `data/`, порт 8000. Деморежим: `app.demo`, `data-demo/`, порт 8001. Mac-файл `Start Demo.command` на Windows не используется.
- Не генерируй «настоящую» статистику без игры и не клади синтетические `fc24-live-editor-lua` JSON в рабочий `data/spool`. Искусственные входы допустимы в изолированных тестах и отдельном демо.
- Сохраняй неизвестные поля как неизвестные. Не заполняй xG, результаты, соперников, минуты, оценки, OVR и другие отсутствующие данные. Дельта счётчиков — изменение между снимками, а не доказанный матч.
- `collector.experimental.lua` выключен намеренно. До реальных проверок не включай verification flags, `verified_live` и `completeness=COMPLETE`. Не меняй статусы P0/P2 на VERIFIED.
- Сейчас **не реализован подтверждённый автоматический `season_reader`**, не определены надёжные события окончательного обновления статистики и не проверен автозапуск скрипта. Установка приложения не устраняет эти неизвестные.
- Не удаляй пользовательскую БД, заметки, сохранения и локальные изменения. Не используй `git reset --hard`, `git clean`, force push или автоматическое разрешение конфликтов данных заменой.
- Чини обнаруженные проблемы Windows точечно, сохраняя архитектуру. Не переписывай UI и коллектор целиком. Синтаксические и автономные Lua-тесты не являются проверкой встроенного Lua Live Editor.

## 3. Установить зависимости и собрать приложение

Все команды выполняй из `$ProjectPath`. Не копируй `.venv` и `node_modules` с Mac. Создай Windows-окружение заново.

Проверяй код возврата каждой нативной команды: `$ErrorActionPreference = 'Stop'` сам по себе не гарантирует остановку при ненулевом `$LASTEXITCODE`. Можно использовать такой helper:

```powershell
$ErrorActionPreference = 'Stop'
function Invoke-Checked {
    param([string]$Program, [string[]]$CommandArguments)
    & $Program @CommandArguments
    if ($LASTEXITCODE -ne 0) {
        throw "Command failed: $Program (exit $LASTEXITCODE)"
    }
}

Invoke-Checked 'py' @('-3.12', '-m', 'venv', '.venv')
$PythonExe = Join-Path $ProjectPath '.venv\Scripts\python.exe'
Invoke-Checked $PythonExe @('-m', 'pip', 'install', '-r', 'backend/requirements.lock')
Invoke-Checked $PythonExe @('-m', 'pip', 'install', '-e', 'backend', '--no-deps')
Invoke-Checked 'npm.cmd' @('--prefix', 'frontend', 'ci')
Invoke-Checked 'npm.cmd' @('--prefix', 'frontend', 'run', 'build')
```

Существующее рабочее окружение можно переиспользовать после проверки Python и зависимостей. Не обновляй lock-файлы просто ради установки. Если конкретная зависимость не устанавливается на Windows, исследуй реальную ошибку и исправь совместимость; не выкидывай тесты, Lua harness или миграции ради зелёного результата.

Проверь существующий `.env`, если он есть, только по нужным параметрам; не печатай его целиком. Настрой для запуска:

Для последующих запусков сохрани соответствующие параметры в локальном `.env`, не перезаписывая посторонние настройки. Записывай конфиги в UTF-8 без BOM. `.env`, БД, локальные пути и bindings не публикуются в Git.

Seed берёт включённый в репозиторий **реальный** `leicester_rebuilt_with_career_totals.xlsx`, только лист `Все сезоны`. Не импортируй сезонные дубли и `За всю карьеру`. На исходном файле ожидаются 123 строки, 82 точных именных идентичности, 5 сезонов, 601 гол, 437 ассистов и 3093 выступления игроков. Это неполная историческая выборка, не полная статистика матчей клуба.

Проверь повторный seed: он не должен менять суммы. Если уже существующие данные конфликтуют, не заменяй их автоматически: выведи конкретные конфликты и сохрани имеющуюся историю.

Ориентир на момент написания задания: 49 backend-тестов и 10 frontend-тестов; при изменении репозитория ориентируйся на фактически собранные тесты и их результат, а не подгоняй число.

Запусти обычный сервер в отдельном терминале или управляемом процессе с сохранёнными stdout/stderr:

```powershell

```

Не жди завершения серверного процесса как теста. Дождись готовности HTTP и проверь:

```powershell

Invoke-RestMethod 'http://127.0.0.1:8000/api/v1/careers'
```

Ожидается `status=ok`, `demo_mode=false`, `collector=not verified`. Открой `http://127.0.0.1:8000`, проверь реальные исторические графики, сезонный фильтр, таблицу, панель игрока и Sync Status. В обычном режиме не должно быть демоплашки или вымышленных игроков.

Убедись, что порт 8000 принадлежит этому приложению и слушает `127.0.0.1`. Не завершай неизвестный процесс, если порт занят. Найди владельца; переиспользуй подтверждённый backend или выбери свободный порт через `HTTP_PORT`, согласованно обновив URL проверки. Не меняй bind на `0.0.0.0`.

Проверка watcher с синтетическими входами проводится в pytest/временной БД. При желании отдельно проверь `app.demo --no-browser` и `npm.cmd --prefix frontend run test:demo`; это остаётся демопроверкой в `data-demo/`.

## 7. Подготовить отдельную карьеру для первой диагностики

Не назначай неизвестный игровой save исторической карьере автоматически. Для первого опыта нужна отдельная карьера, например `FC24 · Live P0`, с собственным binding.

Если известен фактический начальный год карьеры, создай её через UI или `POST /api/v1/careers` с полями `name`, `game_version="EA FC 24"`, `start_year`. `primary_team_id` оставь null до реального подтверждения.

Затем вызови `POST /api/v1/careers/{career_id}/saves/bind` с:

```json
{
  "instance_key": "<новый UUID для конкретного тестового save>",
  "external_save_uid": null,
  "verified_live": false,
  "evidence": null
}
```

Значение ключа генерируется один раз и сохраняется. При повторном запуске подготовки переиспользуй свой известный binding; не создавай дубли. Не меняй binding чужой карьеры. Если начальный год/выбранный save неизвестны, подготовь запросы и отметь недостающие поля; продолжай остальные шаги, не подставляй случайный год.

## 8. Подготовить локальный config.lua и команды диагностики

Создай `collectors/fc24-live-editor/config.lua` из `config.example.lua`, если его ещё нет. Существующий конфиг сначала прочитай и сохрани его полезные настройки.

Нужно настроить:

- `spool_dir`: абсолютный путь к **обычному** `$DataPath/spool`, с `/` в Lua-строке. Не `data-demo/spool`.
- `instance_key`: ключ конкретного тестового save из предыдущего шага.
- `season_start_year`: фактический **текущий** сезон для первого диагностического снимка, если он известен. Это отдельный параметр от начального года карьеры. Не бери его из демо, системной даты или последнего листа Excel. Если неизвестен — оставь nil и отметь, что его надо указать один раз перед первым снимком. Автоматический сезонный reader пока не подтверждён.
- Оставить `enabled`, `transport_verified`, `triggers_verified`, `save_uid_verified`, `context_reader_verified` равными **false**, `verified_event_names={}`, `season_reader=nil`.

Создай папку spool и проверь обычные права записи средствами Windows. Это подтверждает только доступ Python/Windows к папке, не возможность записи из Lua Live Editor. Для пути с кавычками корректно экранируй Lua-строку. Не публикуй локальный config.lua.

Подготовь пользователю **две точные команды с фактическим абсолютным путём**, которые он вставит в Lua Engine уже после загрузки карьеры. Например, только если проект действительно расположен в `C:/Users/NAME/Projects/FootballCareerDashboard`:

```lua
LCA_ROOT = 'C:/Users/NAME/Projects/FootballCareerDashboard/collectors/fc24-live-editor'
dofile(LCA_ROOT .. '/diagnostic.lua')
```

Затем отдельно:

```lua
dofile(LCA_ROOT .. '/event_probe.lua')
```

Не выполняй их сейчас как будто игра уже запущена. `collector.experimental.lua` на этом этапе не запускается. Если найдены реальные установленные `enums.lua`/примеры API, исследуй их для будущей проверки символических констант; наличие константы ещё не подтверждает правильный момент считывания.

## 9. Что остаётся на первый запуск игры — сейчас не выполнять

После отчёта пользователь запустит совместимый Live Editor и FC 24, загрузит **копию** нужной offline manager career. Дальнейший порядок:

1. Уточнить текущий сезон и выставить diagnostic season_start_year, если он был неизвестен.
2. Выполнить diagnostic.lua; проверить реальный JSON и строки своей команды. Первый результат не заменять синтетикой при ошибке.
3. Найти файл в `spool/` либо, если watcher уже его забрал, в `processed/` и `raw/`; проверить snapshots и Sync Status в приложении.
4. Для первого отображения выбрать конкретный турнир: diagnostic отправляет `completeness=UNKNOWN`, поэтому общий Live TOTAL намеренно может показывать `—`. Не включать COMPLETE/verified_live ради появления цифр.
5. Выполнить event_probe.lua один раз и записать последовательность событий. Диагностика до сыгранного матча и после отчётов/возврата в хаб/смены дня установит момент реального обновления счётчиков.
6. Сравнить реальные JSON через `python scripts/diagnose_snapshots.py before.json after.json`; повторить для быстрой симуляции.
7. Позже проверить повтор события, reload/откат, переход сезона и автозапуск. По подтверждённому источнику реализовать автоматический season_reader и проверить точные triggers. До этого автоматический collector остаётся экспериментальным и выключенным.

Первые диагностические запуски — временный POC. Постоянного ручного экспорта или загрузки скриншотов в основном игровом процессе быть не должно.
